# Architecture

## Projects and responsibilities

The root [solution](../Mockarium.slnx) groups application projects under
`src/` and the test suite under `tests/`.

- **Mockarium.Core** owns domain models, SQLite persistence, studio operations,
  fixture data, validation, execution history, and the MCP server runtime.
- **Mockarium.ViewModels** contains the shared CommunityToolkit.Mvvm view models,
  commands, draft tracking, and cross-studio application state.
- **Mockarium.Wpf** is the Windows WPF client.
- **Mockarium.Desktop** is the Avalonia client for macOS and Linux.
- **Mockarium.Tests** covers storage, view-model behavior, MCP calls, and
  headless Avalonia interactions.

Both desktop clients reference the same view models and core services. UI
platform differences stay in the clients and their platform-service adapters;
the shared domain layer does not depend on either UI framework.

## Persistence

`MockariumStore` owns a SQLite connection and serializes access with a
connection-level lock. It creates the schema on startup and performs explicit
schema migration where needed. Workspace data includes mock-server
configuration, studio data, settings, and bounded execution history.

Email, Database, and Calendar operations validate input at the storage/service
boundary. Database table and field identifiers are validated; model data is
stored as JSON, and no agent-facing operation executes raw SQL. Calendar
instants are stored in UTC and availability calculations respect participants'
time zones and working hours.

The default database location is
`Environment.SpecialFolder.ApplicationData/mockarium/mockarium.sqlite`, matching
the Electron source package name. An existing database under the alternate
`Mockarium` directory is also recognized; two distinct databases cause an
explicit startup error rather than an implicit choice. A compatibility test
opens a SQLite database generated by the Electron store and verifies all studio
data and execution history. Packaged user-data paths still need verification
on every supported OS before in-place reuse can be guaranteed.

## Runtime and observability

`McpRuntime` hosts the registered tools using the .NET MCP SDK and Streamable
HTTP. Listeners bind to loopback and validate request origins. Tool execution
records actual inputs, results or errors, and duration in local history; the
shared view models deliver those events to Live Inspector. Nullable input types
use equivalent JSON Schema `anyOf` branches instead of type arrays, preserving
explicit `null` values while improving compatibility with schema consumers.

Servers operate only on simulated local data. The application does not send
workspace data to external services.

## UI and drafts

View models own navigation, editor state, asynchronous commands, and
unsaved-change checks. Studio refreshes update only the relevant collections
where possible, preventing one editor's save from replacing drafts in another.
Destructive actions and selection changes request confirmation where drafts
could be lost.

Both clients use the same studio view models and provide a visual week planner;
keyboard-accessible agenda controls remain available for calendar editing.
Editor fields, lists, and ambiguous actions expose accessible names in both
clients. Screen-reader and platform-specific accessibility validation remain
part of the release review.
